# Rat Race: Running the Demand Model (ONNX) in the Game

This document tells you everything needed to call the demand-forecasting model
from the game backend. It is addressed to the agent integrating the model, not
to the ML pipeline owners. If you are touching the model itself, see
`ml/config.py`, `ml/train.py`, `ml/export.py`, and the `ml/data/` builders.

---

## 1. What the model predicts

The game plays out as a replay of *historical NYC taxi demand*. There are **12
regions** (see `game_zones.json`). A game lasts **3 days x 4 turns = 12 turns**,
at wall-clock cutoffs **08:00 / 11:00 / 14:00 / 17:00** (America/New_York local).
At each turn the backend asks for one demand forecast per region per horizontal
horizon:

- horizon **1h**, **2h**, **3h** ahead of the cutoff.

Each prediction is the **number of pickups** (all 4 TLC services combined:
yellow, green, FHV, FHV-HV) counted in that **single future hour bucket** for
that region. It is a raw count (not normalized). Typical scale on the holdout:
region × hour means around **3.9k–4.1k** pickups, std ~2.7–2.9k, but a small
region (e.g. Staten Island) is far below that.

There are four ONNX graphs, all sharing the exact same 13-feature input:

| file              | objective       | meaning                                   |
|-------------------|-----------------|-------------------------------------------|
| `demand_mean.onnx`| regression      | expected demand (conditional mean)        |
| `demand_p10.onnx` | quantile α=0.10 | 10th-percentile (low) forecast            |
| `demand_p50.onnx` | quantile α=0.50 | median forecast                           |
| `demand_p90.onnx` | quantile α=0.90 | 90th-percentile (high) forecast           |

> The p10/p50/p90 come from quantile-regression objectives, not from a
> distribution over the mean. They are independent models. Verified holdout
> coverage on the shipped variant: p50 ≈ 34%, p90 ≈ 73% — the tails are
> under-dispersed, treat p10/p90 as "low"/"high", not as true confidence bounds.

## 3. Input format (the only contract that matters)

One input tensor per model: **`float32`, shape `[N, 13]`, in exactly the order
below**. Column order is the source of truth in `feature_columns.json` — never
hard-code it.

| # | column          | type   | meaning / how to obtain it                                              |
|---|-----------------|--------|------------------------------------------------------------------------|
| 0 | `hour`          | int    | cutoff hour 0–23, New York local time                                  |
| 1 | `dow`           | int    | day of week **0=Monday … 6=Sunday** (Python/pandas convention)          |
| 2 | `temp_c`        | float  | temperature (°C) at the cutoff, region level                           |
| 3 | `wind_ms`       | float  | wind speed (m/s)                                                        |
| 4 | `vis_km`        | float  | visibility (km)                                                         |
| 5 | `precip_mm`     | float  | precipitation (mm) in the hour leading up to the cutoff                 |
| 6 | `precip_3h_mm`  | float  | precipitation (mm) over the previous **3 hours** (incl. the cutoff hour)|
| 7 | `event_count`   | int    | # GDELT events citywide **yesterday**                                   |
| 8 | `event_mentions`| int    | total raw mention count of those events                                 |
| 9 | `avg_tone`      | float  | mean news tone (−100…+100; usually −10…+10)                             |
| 10| `avg_goldstein` | float  | mean Goldstein scale (−10…+10 confidence/cooperation)                   |
| 11| `horizon`       | int    | 1, 2, or 3 (hours ahead of the cutoff; not 0-based)                     |
| 12| `zone_id`       | int    | numeric region code – **must come from `zone_codes.json`**              |

### 3.1 Point-in-time rules (do not break these)

- **Weather** is stamped onto the cutoff **as-of** (no lookahead): the values
  above are the ones known *at* the cutoff.
- **News** is joined with a **1-day lag**: for a cutoff on day D you must use
  the news aggregate of day **D−1**. Using same-day news is a leak and changes
  the predictions.
- **No demand features exist.** The game model deliberately has no leverage on
  trip counts, lags, or neighbor flows. Do not try to pass them.
- There is no separate weather/season calendar passed in: the model infers
  time-of-year from the temperature. Feed real hourly weather.

### 3.2 Where to source features for the replay game

Because the game replays historical dates, the simplest correct source is the
pipeline's own feature tables (same tables the model was trained on):

- Weather per region + hour: read `ml/data/weather_hourly.parquet`
  (`hour`, `game_zone`, `temp_c`, `wind_ms`, `vis_km`, `precip_mm`);
  compute `precip_3h_mm` = trailing 3-hour rolling sum per region.
- News per day: read `ml/data/events_daily.parquet`; for cutoff day D take the
  row with `date == D − 1`.
- `zone_id`: `zone_codes.json` (`"zones": {slug: code}`).
- `dow`: `datetime.weekday()` on the cutoff date (0=Monday).

These files sit under `ml/data/` and are regenerated by `python -m ml.data.weather`
/ `python -m ml.data.gdelt`. If the backend instead has live weather/news
sources, convert them with the same units above.

## 4. Inference

Use `onnxruntime` (a single-light dependency). The input node is named
**`input`**, output is a 2-D float tensor `[N, 1]` with one prediction per row.

```python
import json
from pathlib import Path

import numpy as np
import onnxruntime as ort

MODELS_ROOT = Path("ml/models")

sessions = {
    name: ort.InferenceSession(str(MODELS_ROOT / f"demand_{name}.onnx"),
                               providers=["CPUExecutionProvider"])
    for name in ("mean", "p10", "p50", "p90")
}

def predict(zones: "list[str]", hour: int, dow: int, horizon: int,
            weather: dict, events_yesterday: dict) -> dict:
    """One forecast for one (hour, dow, horizon) across all regions.

    weather:        {game_zone: (temp_c, wind_ms, vis_km, precip_mm, precip_3h_mm)}
    events_yesterday: dict with keys event_count/event_mentions/avg_tone/avg_goldstein
    """
    feature_cols = json.loads((MODELS_ROOT / "feature_columns.json").read_text())["features"]
    zone_codes = json.loads((MODELS_ROOT / "zone_codes.json").read_text())["zones"]

    rows = []
    for gz in zones:
        t, w, v, p, p3 = weather[gz]
        rows.append([
            hour, dow, t, w, v, p, p3,
            events_yesterday["event_count"], events_yesterday["event_mentions"],
            events_yesterday["avg_tone"], events_yesterday["avg_goldstein"],
            horizon, zone_codes[gz],
        ])
    X = np.asarray(rows, dtype=np.float32)          # [N, 13] float32

    out = {}
    for name, sess in sessions.items():
        pred = sess.run(None, {"input": X})[0].ravel()   # [N]
        out[name] = {gz: float(pred[i]) for i, gz in enumerate(zones)}
    return out
```

Notes:

- **Always cast to `float32`.** Convert *before* creating the tensor. Model
  split thresholds live in fp32; feeding float64 magnitudes then having ONNX
  round them can push borderline rows into the wrong leaf. float32 is exactly
  the distribution the model was trained on (parity gate enforces it).
- **Batch anything you like.** There is no constraint on N; rows can mix
  regions and horizons freely.
- Output is directly comparable to future hour *counts*, i.e. nothing to scale,
  exponentiate, or clip. You may clamp tiny/negative quantile outputs to ≥ 0.

### 4.1 Full per-turn call

A turn produces `12 regions × 3 horizons × 4 model variants = 144` numbers; the
game only needs what it shows, but the shape is:

```python
def forecast_turn(cutoff: "datetime.datetime", weather, events_yesterday):
    hour, dow = cutoff.hour, cutoff.weekday()
    zones = json.loads((MODELS_ROOT / "game_zones.json").read_text())["zones"]
    slugs = [z["game_zone"] for z in zones]
    result = {
        h: predict(slugs, hour, dow, h, weather, events_yesterday)
        for h in (1, 2, 3)
    }
    return result  # result[horizon][variant][slug] = count
```

(Compute hour/dow in America/New_York wall time; the pipeline uses naive local
timestamps.)

## 5. Sanity checks

- **Order matters.** If rows deviate from `feature_columns.json`, predictions
  silently change. Assert `len(X[0]) == len(feature_columns["features"])`.
- **Magnitude.** On replay dates, mean-model outputs per region are typically
  in the low thousands; Staten Island can be a few hundred. Values in the tens
  of thousands or negative (after clamping → 0) indicate a feature bug.
- **News lag check.** Changing `events_*` between D−1 and D rows must not change
  the output (they are not features).
- **Parity.** Native (joblib) vs ONNX is validated at build time: max absolute
  deviation < 1e-2 pickup, 0 rows off by more than 1. If you ever see a large
  mismatch, it is an input-shape/order/dtype problem, not the model.

## 6. Changing the model

The artifacts are the single source of truth for play. If the region set,
feature set, or replay window ever changes, the pipeline must be rebuilt
(section 2 commands) and the new JSONs re-committed alongside the code. The
`ml/` pipeline is owned separately — coordinate before editing
`ml/config.py` / `ml/data/zones.py`.
